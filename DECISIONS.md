# Decision register — the toolsmith conventions

Operative form only: one line of decision, one line of rationale.
Amendments are folded into the operative text with an italic
parenthetical; closures rewrite the entry. Full context lives in the
session records and source repos, never here. This register is how the
conventions evolve: a change to CONTRACT.md cites the T-number that
authorized it.

| # | Decision |
|---|---|
| T1 | The repo is named `toolsmith`. "Chassis" stays the name for the code layer inside each tool (the conventions every verb inherits). |
| T2 | Tools share the contract, not a library. Chassis code is copied per tool; the written contract keeps copies aligned. No cross-repo version coupling. |
| T3 | Every conversion target becomes a Go binary. No lighter "asset pack" tier; prose-heavy tools carry their prose as assets next to a small binary. |
| T4 | The skeleton is a compiling Go module using `toolname` / `TOOLNAME` / `toolnameerr` as placeholders, instantiated by `contrib/new-tool.sh`. A compiling skeleton can be smoke-tested green; a text-template one rots silently. |
| T5 | `exitcode.Silent` is part of the chassis contract (C2.4). Ratified from ste9: a byte-parity verb cannot let the error renderer own its stderr. |
| T6 | Drift vocabulary is duo's six states — `current, missing, stale, modified, unowned_conflict, incompatible` (C4.5). wip's per-file added/removed/changed is the floor and maps in. |
| T7 | The manifest carries a self-committing `manifest_digest` (C3.4), adopted from duo: it makes the manifest a comparable identity. |
| T8 | The manifest declares its contract version (`"contract": "toolsmith/v1"`, C3.6), so conformance is read from the tool, not asserted from memory. |
| T9 | "Manifest" is reserved for the verb-surface self-description; the install-state file is the "stamp" (C3.5). ste9 used "manifest" for install state and proved the collision. |
| T10 | Splice targets are a ratified install-target class (C4.8): marker blocks for text, gjson/sjson surgical edits for JSON, one-time backup, byte-golden tests. From ste9's CLAUDE.md/settings.json work. |
| T11 | Emit-only targets are a ratified install-target class (C4.8): render for pasting, install nothing, stamp nothing. From ste9's desktop target. |
| T12 | Per-target variant flags are permitted where targets genuinely differ (C4.8), shaped `--<asset> <target>=<variant>,...`. From ste9's register variants. |
| T13 | A materialized data dir is a ratified artifact class (C4.9): write-side, stamped, drift-checked, distinct from the read-side asset chain. From ste9's greppable references. |
| T14 | Port specs live at `docs/<matter>/port-spec.md`, committed (C7.2). ste9's port spec stranded in an ephemeral scratchpad while shipped comments cited it. |
| T15 | `make hooks` installs both pre-commit stages (C6.6). wip shipped the one-stage gap; ste9 fixed it; the skeleton ships the fix. |
| T16 | GitHub Actions are SHA-pinned in the skeleton workflows (C6.5). From duo main. |
| T17 | Reusable (workflow_call) GitHub workflows are rejected for v1: cross-repo coupling cuts against T2. Revisit only if copy drift demonstrably hurts. |
| T18 | The skeleton ships exactly one worked harness target (claude-code). Additional targets follow assets/playbook/new-harness-target.md; six near-verbatim copies in wip showed shipping all of them teaches nothing extra. |
| T19 | Phase B — the `toolsmith` binary (`new`, `check`, `manifest`, `doctor`) with the skeleton as its embedded asset tree — is deferred until Phase A has run one real conversion (*amended: that conversion is toolsmith's own, tracked as the `toolsmith-binary` Matter; clast remains the acceptance test of intake, the orphan branch, and cutover, tracked as `clast-conversion`; neither Matter blocks the other*). The shell scripts are the parity oracle it must match before they retire, and only a self-conversion exercises that retirement — clast never touches them, and no clast source is recorded on any host. |
| T20 | Contract versioning: additive clauses bump the minor, breaking changes bump the major. Tools pin the version they conform to in their manifest (*amended by T24: the minor lives in CONTRACT.md's clause history, and the version a tool declares carries the major alone*). |
| T21 | The conformance checker reports findings by clause ID, flat, exhaustively, exit 0/1 — the same shape as a tool's `doctor` (C4.7). |
| T22 | `assets/handoff-kit/` states its model separately from its medium. `HANDOFF.md` and `SEED-CARDS.md` are always files in the sidecar; the Matter register and the workplans are model, and live in `workplans/<slug>.md` when the conversion has no tracker or in the tracker when it has one, with the sidecar naming which. The kit borrowed wip's vocabulary and wip's filesystem together — a conversion run without a tracker needs the directory, and one run with a tracker needs the tracker to be the single copy. |
| T23 | The manifest records each verb's positional-argument usage verbatim from its declaration (`usage`, C3.8), never parsed into structure. Found in toolsmith's own conversion: the first two verbs with a meaningful positional rendered in the generated claude-code skill as bare verb names, so an agent reading the projection could not tell that `new` requires one. The angle/bracket convention the declaration uses is enforced by nothing, so splitting it into fields would be inventing structure — C3.7's prohibition applied to arguments. |
| T24 | The contract's minor version lives in CONTRACT.md's clause history; the string a tool declares (C3.6) carries the major alone. Conformance is **derived** — the checker reports which clauses it audited and how they fared — rather than self-declared, and the checker's coverage is stated as partial rather than implied to be total. Measured, not assumed: nothing reads the version digits today — the oracle greps `"contract":"toolsmith/` and the port tests `strings.HasPrefix(m.Contract, "toolsmith/")`, so `toolsmith/banana` passes C3.6 as readily as `toolsmith/v1`. A declared minor would add digits no consumer reads while manufacturing the cross-repo version coupling T2 exists to prevent, and it would stay a self-report that can be wrong in both directions. Deriving instead is what T8 was actually reaching for: a self-declared version is still asserted from memory, just the tool author's. Precedent: `SchemaVersion` already answered this same question the same way, bumping only on incompatible change because every harness bakes it into its SKILL.md. |
| T25 | A tool records the contract minor it was last reconciled against, so the checker can name the clauses added since and call the reading pass stale. This is the one consumer a minor version has: it verifies that the human pass `migrate.md` Stage 8 mandates actually ran and is current, not that the tool conforms. Self-reported like any version, but it reports a process fact ("I read the contract at v1.1") rather than a semantic claim ("I conform"), so it is hard to get accidentally wrong and it fails as visible staleness rather than silent falsehood. |
| T26 | C2.5 sanctions exactly one error code outside its five prefixes: `<verb>.findings-present`, exit 1, for a verb whose run completed and whose own findings are the verdict (`doctor` under C4.7, `check` under T21). The findings stay on stdout as the payload, which C2.2 now names as its one exception (*contract-v1-2-reconcile step-05*). A verdict is not a failure of the verb, so no prefix names it. The form mirrors C2.4's one sanctioned extension, `exitcode.Silent`. Every existing tool already emits `doctor.findings-present`, so the additive form (v1.2) keeps them conformant with no cross-repo change (T2). Rejected: `validation.findings-present`, which bends a prefix wip uses 86 times for input checks, and forces a rename in every tool for no gain in meaning. |
| T27 | C4.4's "hand-written content" means prose. The fixed template text a generator writes around manifest fields (headings, labels, and format strings such as claude-code's `plugin.json` description suffix) is generated output, and it stays in code (*contract-v1-2-reconcile step-11*). A clarification, not a new requirement, so it takes no clause-history row (T20). Found in toolsmith's own reconciliation pass, which read the suffix as a C4.4 divergence. A format string is not tunable prose (C5.1), and an override of one could make the generated file invalid. The skill description is prose, so it moved to an asset. |
| T28 | The binary serves CONTRACT.md, the playbook and the handoff-kit through `toolsmith doc [path]`, a plumbing verb, and shipped prose names them by doc name (`playbook/intake.md`), never by repo path (*doc-verb step-01*). CONTRACT.md is embedded from the repo root and served only from the compiled copy, because it is the spec this binary's `check` audits against, not tunable behavior (C5.1); for the same reason it stays out of the manifest's asset list. The playbook and the kit are assets already, so they resolve through the asset chain. Found when `clast-conversion` set out to dogfood the installed binary: the skill promised the playbook "without cloning anything", but no verb read it, only the nix package wrote it to disk, and the contract did not ship. Rejected: a C4.9 data dir (install, stamp and drift machinery for a need that a stdout reader covers); references inside the claude-code skill (they reach one harness); moving CONTRACT.md under `assets/` (about 50 references name it at the root); a second copy behind a drift test (one copy, per the handoff-kit). |
| T29 | C3.2's retroactive decision record — the entry the extracted v1.0 body never had (*porcelain-plumbing-ratify step-01*). The kind annotation carries the determinism axis alone — `plumbing`, `llm`, `control-plane` — and it stands unchanged. Its phrase "the porcelain/plumbing split" is narrower than the words suggest. In clast, the concept's source, porcelain named the public user API: a workflow shape shipped in two lockstep delivery forms, CLI verb and harness skill. That audience meaning was dropped in three steps: the ancestral architecture doc reframed porcelain in the git sense, as hand-written surfaces whose drift generation should eliminate; wip D47/D53 reassigned the word to the transport axis; the contract then inherited wip's package comment verbatim — the mechanism without the rationale — and C3.2 became the definition of a concept it was only the enforcement point of. The cost is measured (docs/lineage/porcelain-plumbing.md, 04de830): ninety annotated verbs across four tools, every one `plumbing`, the other kinds exercised only by test fixtures; and in old clast, flow logic that lived in only one delivery form drifted invisibly (a stale inlined brief prompt, a never-built retro skill). The dropped audience axis returns as surface structure, never as a kind change: the shape clause and the `plumbing` namespace, proven in the clast conversion (clast-reboot SURFACE.md V1–V12, owner decisions S8–S10) and ratified by this Matter's later steps. |
| T30 | Shapes are a contract concept (C8.1–C8.2, v1.3; *porcelain-plumbing-ratify step-02*). One named workflow, defined once in a live-served flow asset (`assets/flows/<shape>.md`), delivered twice: a top-level `llm` verb, and a projected skill whose core instruction is to read the flow and follow it. The push-down rule beside it: every deterministic step a shape needs is reachable through `plumbing`-kind verbs; the verb form may hold private state, never private logic. This ratifies the substance of clast SURFACE.md V6–V7 (owner decision S9) after the conversion proved it in use — the S10 sequencing: clast proves, the contract ratifies. It restores the half of the original porcelain concept T29 records as dropped, and closes the structural gap the lineage doc names: the flow asset is the one object linking a shape's two forms, where before the halves filed under unrelated clauses and drifted invisibly (a stale inlined brief prompt, a never-built retro skill). Rejected: rendering the flow into SKILL.md at install — self-contained offline, but overrides would apply only on re-install, the same trade the asset chain already refuses; and leaving shapes tool-local — the drift was cross-tool discipline failing, which is exactly what the contract exists to make structural. |
| T31 | The `plumbing` namespace is the audience boundary (C8.3–C8.4, v1.3; *porcelain-plumbing-ratify step-03*). One binary; bare `--help` shows only porcelain; the substrate is `<tool> plumbing <verb>`; the manifest records qualified names under C3.8. Shape names reuse across the boundary — `<tool> <shape>` is the shape, `<tool> plumbing <shape>` its deterministic document — which dissolves invented sibling names like draft-1 clast's `retro-data`. The label was challenged (`plumb`, `pb`) and kept: the token argument dissolved on inspection (all three tokenize to ~1 token in command position), and `plumbing` is the exact C3.2 kind string and the git term of art (lineage doc §7). Ratifies the substance of clast SURFACE.md V1–V3 and V8 (owner decision S8) after the conversion proved it in use, per S10. Scope: a tool that ships shapes draws the boundary; retrofitting an existing flat surface (the wip back-port sketch, lineage doc §6.4) is that tool's own decision and is deliberately not decided here. Rejected: a second binary (`<tool>-plumbing`, the bash architecture) — it breaks the one-binary posture and strains C1.2/C3.1/C4.1 (two stamps, two versions, manifest ownership) for a wall barely taller than the namespace. |
| T32 | Verb pairs and the `alias-of` manifest field are ratified (C8.5, C3.9, v1.4; *verb-pairs-ratify*). Where the C8.3 boundary stands, a verb may register in both trees when both audiences need it; three questions decide placement — does a human type it unprompted, does a skill or script call it for its own operation, and when both are yes, is the deliverable the same for both audiences. Same deliverable → an alias pair: one implementation, one constructor registered twice, identical flags, output, schema, and kind, with a golden test pinning byte-sameness and diagnostics canonicalizing to the plumbing spelling. Different deliverable → a split pair: the top-level member is the finished, human-sized form, the plumbing member the deterministic substrate it is built on; the pair splits on the human face only — `--json` is one contract. `alias-of` lands on the porcelain member alone, naming the canonical member's qualified name; the canonical member and both split-pair members carry nothing — a different deliverable is not an alias. Ratifies clast SURFACE.md's V1 amendment (2026-09-14, owner call) after wip proved it end-to-end (D112: `wip next` byte-equals `wip plumbing next`; `wip status` splits the human face while `--json` is byte-identical), per the S10 sequencing. C4.3 gains a clarification riding the decision: the projectable set is the namespace's `plumbing`-kind members — the two axes conjoined — so a pair reaches a skill table through its canonical member alone. Rejected: `alias-of` on the canonical member (inverts a self-contained registration, and one field cannot hold several porcelain spellings); a symmetric link (drift-prone redundancy); a separate pairs section in the manifest (a parallel registry, the failure mode the annotation-on-command mechanism exists to avoid); hiding the porcelain member from the manifest (C3.1's self-description must stay complete). |
